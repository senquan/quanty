## 0. 一句话结论

wechatDownload 提供**本地 MCP（`127.0.0.1:4545/mcp`）**，且 **dc / backend / 该工具三者在同一台 Windows 机器上**（证据：`backend/app/core/config.py:55` `INTEL_CLEANER_BASE_URL = "http://127.0.0.1:8100"`）。

因此可以**由 dc 直接 HTTP 调 MCP** 完成「提取公众号 id → 批量下载历史 → 每日增量拉取 → 导出 md → 入库」。

但**真正的拦路虎不是下载，是解析**：现有 `.md` 解析路径（`app/intel/ingest/manual.py:273`）**只拿文件名当标题，`author` 恒为空**，而画像正是按 `author` 分组 —— 照现状接入，271 篇公众号文章会全部归入"无作者"，**画像功能等于没做**。

所以本方案的重心是 **P0 解析层（零 MCP 依赖，可独立验收）**，MCP 接入放在 P1。

### 2.3 实测：wechatDownload 的 md 导出长什么样

对 `docs/repos/wechatDownload/example/` 下 9 个真实导出 md 逐一检验，**格式并不统一**：

| 文件 | `# 标题` | 作者行格式 | 日期 | `__biz` | 本文 URL |
|---|---|---|---|---|---|
| `20240705…307…md` | ✓ | 旧版 `原创  阮一峰  [ 阮一峰的网络日志 ](javascript:void\(0\);)` | ✗ | ✓(4) | ✗ |
| `20241101…323…md` / `20250110…333…md` / `…304…md` | ✓ | 旧版（同上） | ✗ | ✓ | ✗ |
| `[2026-08-14-0843]…408…md` | ✓ | **新版** `原创  阮一峰  阮一峰  阮一峰的网络日志`（无方括号） | **✓** `_2026年08月14日 08:43_ … 云南` | ✓(4) | ✗ |
| `科技爱好者周刊289….md` | ✓ | **★** 作者行是 `**阮一峰的网络日志**` | ✗ | ✓(5) | ✗ |
| `科技爱好者周刊#276….md` | **✗**（标题是缩进纯文本行） | ✗ | ✗ | **✗(0)** | ✗ |
| `[2025-12-20225424]田.md` | **✗** | ✗ | ✗ | **✗(0)** | ✗（内容近乎空，疑似导出失败残留） |
| `特斯拉被曝…Model2马斯克.md` | **✗** | ✗（是 163.com 网页导出的 nav 菜单） | ✗ | ✗ | ✗（**非微信 md 混入**） |

**由实测得出的三条硬约束**：

1. **`# 标题` 不是必然存在**，作者行有 **3 种以上格式**，日期行**仅新版才有** ⇒ 解析必须逐条降级，不能硬匹配单一正则。
2. **`__biz` 在 md 里能拿到，但来源是正文末尾的「往期推荐」链接**（如 307.md:436 `](http://mp.weixin.qq.com/s?__biz=MzI4NjAxNjY4Nw==&mid=…)`），**不是本文 URL** ⇒ 公众号 id 可提，**本文 canonical_url 提不到**。
3. **md 的元数据不可靠但可作降级来源**；**权威元数据在 CSV**（`export_article_data` 产物，见下）。

CSV 实测格式（`example/2024-12-07-231605.csv`）：

```csv
title,url,time,like_num,read_num,share_num,comment_count
科技爱好者周刊#328：AI 模型不是一门好生意,http://mp.weixin.qq.com/s?__biz=MzI4NjAxNjY4Nw==&amp;mid=2650239213&amp;idx=1&amp;sn=…,2024-12-06 08:35:06,179,15984,481,46
```

⚠️ **两个坑**：① `url` 里的 `&` 被 HTML 转义成 `&amp;`，**解析前必须 `html.unescape`**；② CSV 的 `time` 是**准确发布时间**，比 md 的日期行可靠。

### 2.4 四个缺口

| # | 缺口 | 现状证据 | 影响 |
|---|---|---|---|
| **G1** | **`.md` 解析丢元数据** | `manual.py:273-295` `_parse_plain`：标题=文件名 stem、`author=""`、`published_at=None` | **最严重**：`documents.author` 全空 ⇒ 画像按 author 分组失效 ⇒ R3 直接落空 |
| **G2** | **公众号 id 无处存** | `intel.sources` 仅 `url`（合成键 `wechat://<name>`），无 `__biz` 字段（`migrations/011_intel_schema.sql:11-21`） | R1 无处落地，无法按号去重/续拉 |
| **G3** | **无"调 MCP 拉取"能力** | 现有通道只有"上传文件"与"扫目录"，无任何 HTTP 客户端 | R2 批量/订阅无法实现 |
| **G4** | **CSV 元数据未利用** | `manual.py:124` `_csv_urls()` 只取 URL 列，其余列丢弃 | 白白扔掉权威 title / time / `__biz` |

## 3. 关键决策

### D1. 接入方式：**dc 直连 MCP 为主 + 目录 watch 兜底**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. dc 直连 `127.0.0.1:4545`** | 三服务同机（已证实）；进度/错误可回传前端；无需人工中转文件 | 需工具常开 + 勾「启动MCP」 | ✅ **主路径** |
| B. 后端直连再由 dc 转发 | 与 RSSHub 转发形态同构 | 多一跳无收益（**同机**，dc 直接调更短） | ❌ |
| C. 前端浏览器直连 `4545` | 无需后端改造 | 跨域、凭证暴露给浏览器、后端无审计 | ❌ |
| D. 只做目录共享 | 零依赖 MCP | **无法"立即下载/看进度"**；下载完成时机不可知 | ✅ **保留为兜底**（复用现成 `run_wechat_watch`） |

**落地**：dc 新增 `app/intel/ingest/wechat_mcp.py`；`run_wechat_watch` **原样保留**，MCP 不可用时前端提示"改用目录投喂"。

### D2. 公众号 id：**优先从 URL 解析 `__biz`，MCP `get_public_account_id` 只解决"凭证"**

- `__biz`（如 `MzI4NjAxNjY4Nw==`）**就在文章 URL 里**，base64 编码 ⇒ **零成本、可离线、不需要 MCP**。
- 优先级：① 上传的 CSV/URL 清单（本文 URL，最准）→ ② md 正文「往期推荐」链接（同号，够用）→ ③ 用户手填。
- ⚠️ **`get_public_account_id` 与"提取 id"是两件事**：它拿的是**拉取凭证（密钥）**，且必须在微信客户端点链接，**无法无人值守**。首轮必须人工做一次，之后凭证可复用（会过期）。

### D3. 每日增量：**`export_article_data` 元数据差集 → 逐篇 `single_article_download`**

因为 `batch_download_articles` **无参数**（范围锁在 GUI），"每日读最新"有两种做法：

| 方案 | 机制 | 评价 |
|---|---|---|
| **① 元数据差集 + 逐篇下载** | `export_article_data` 拿全量 CSV → 与库内 `documents.canonical_url/external_id` 差集 → 新 URL 逐篇 `single_article_download` | ✅ **推荐**：范围完全由我们控制，可精确到篇，幂等天然 |
| ② GUI 设"最近 N 天"后调 `batch_download_articles` | 靠 GUI 里的时间范围 | ❌ 依赖人工改 GUI 配置，与"定时无人值守"矛盾；且无法知道这轮下了哪几篇 |

**历史批量**（R2 前半）仍走 `batch_download_articles`：**一次性**操作，允许人工先在 GUI 里设好日期区间，前端提供「打开工具 → 设范围 → 触发下载」的分步引导。**下载落地后再走统一的目录/上传通道入库**（不追求 MCP 直传正文）。

> 即：**MCP 负责"产文件"，现有链路的"解析入库"完全不动**。这样 MCP 只是新增一个**上游生产者**，下游零改动风险。

### D4. md 元数据：**新增 md 感知解析器 + CSV 配对（可选）**

- 新增 `wechat_md.py`：按 §2.3 实测做**逐条降级**解析（标题 → 作者行 3 种格式 → 日期行 → 兜底文件名）。
- `.md` 在 `manual.py:_parse_file_multi()` 里**分流**到新解析器（**不再走 `_parse_plain`**）。
- **CSV 配对**：同批上传含 `wechatDownload` 的 `export_article_data` CSV 时，用 `title` 建索引补 `url`(⇒`__biz`) 与 `time`（⇒`published_at`）。md 自身有日期时以 `time` 为准。

### D5. 媒体文件：**显式关闭**

- 下载配置：`图片/音频/视频` 全关，只留 `MD: True`（+ 可选 `CSV: True`）。
- 解析端：md 里的 `![](url)` 由 `normalize_text()` 的 `_MD_IMAGE_RE` 处理为**只留 alt 文本**（`normalize/text.py:27`），**媒体永不进库**。
- 这样 R4 天然满足，且顺带避免「同一篇 html/md 双副本因图片 URL 导致 simhash 距离 9 漏判转载」的老坑（`normalize/text.py:22-26` 已记录）。

## 4. 数据结构变更（迁移 `019_intel_wechat_accounts.sql`）

### 4.1 `intel.sources` 扩列（**扩列而非建新表**）

理由：`sources` 已是唯一的"源登记处"，`source_type='wechat'` 已存在；新建表会分裂"一个公众号是不是一个源"的口径。

```sql
ALTER TABLE intel.sources ADD COLUMN IF NOT EXISTS external_key  TEXT;   -- 公众号 id（__biz），非微信源为 NULL
ALTER TABLE intel.sources ADD COLUMN IF NOT EXISTS display_name  TEXT;   -- 公众号显示名（作者行/CSV 得到）
ALTER TABLE intel.sources ADD COLUMN IF NOT EXISTS last_pull_at  TIMESTAMPTZ;  -- 最近一次订阅拉取时刻
ALTER TABLE intel.sources ADD COLUMN IF NOT EXISTS pull_state    TEXT;   -- idle / pulling / need_credential / failed
ALTER TABLE intel.sources ADD COLUMN IF NOT EXISTS pull_error    TEXT;   -- 最近一次失败原因（截断 500 字）
-- __biz 全局唯一：同号多别名时靠它归并（partial index，避免 NULL 参与唯一性）
CREATE UNIQUE INDEX IF NOT EXISTS uq_intel_sources_external_key
    ON intel.sources(external_key) WHERE external_key IS NOT NULL;
```

⚠️ **`external_key` 不加 `NOT NULL` / 不用表内 UNIQUE**：与 `uq_intel_sources_url` 同款教训（011 注释已记：表内 UNIQUE 对已建表环境不生效），统一用**部分唯一索引**。

## 6. API 设计

### dc 侧（`data-cleaner/app/intel/api.py`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/wechat/mcp/status` | 工具是否可达（`mcp_available()`）、凭证是否就绪、下载目录、提示语 |
| GET | `/wechat/accounts` | 公众号清单：`id/name/externalKey/enabled/docCount/lastPullAt/pullState/health`（**照 `_rsshub_rows()` 的 LATERAL 取最新 health 写法**） |
| POST | `/wechat/accounts` | 登记：`{name, biz?, url?}` —— 从 url 提 `__biz`，**默认 `enabled=false`** |
| PATCH | `/wechat/accounts/{id}` | 改名/启停（⚠️ **必须显式 `store.update_source(id, enabled=…)`**，不能只靠 `upsert_source`，`ON CONFLICT(url)` 不更新 `enabled` —— 见 `store.py:215` 注释） |
| DELETE | `/wechat/accounts/{id}` | 删除；**有文档则 409**（照 `rsshub_delete_source` 口径 `api.py:526`） |
| POST | `/wechat/accounts/{id}/pull` | 立即拉取一轮（同步长任务，放线程池；返回本轮 new/dup/reposts） |
| POST | `/wechat/probe` | 试解析：上传/粘贴一篇 md 或 URL，**只看解析结果（标题/作者/日期/__biz）不入库** —— 与 `/rsshub/test` 同款"先验再登记" |
| POST | `/wechat/credential` | 触发 `get_public_account_id`，回传需在微信打开的链接与当前状态 |

### backend 侧

同构转发全部 8 个端点至 `INTEL_CLEANER_BASE_URL`，**错误码原样透传**（400/409 不能被吞成 500）。

## 9. 风险与未决

### 9.1 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **凭证过期 / 半自动** | `get_public_account_id` 必须在微信客户端点链接，**无法无人值守** | `pull_state='need_credential'` 显式暴露；订阅失败只记 health 不静默 |
| **`batch_download_articles` 无参数** | 范围锁死在 GUI，MCP 无法按需指定 | 历史批量走"人工设范围 + 目录入库"；增量走 D3-① 差集逐篇 |
| **md 格式随版本漂移** | 实测已见 4 种；上游更新会打破正则 | 逐条降级 + `WECHAT_MD_VERSION` 常量 + 真实样例回归用例 |
| **频率限制 / 账号风险** | 第三方工具抓取，README 自带免责声明 | 单号单轮 `PULL_LIMIT` 限流；默认**不自动开**订阅（同 RSSHub 保守策略） |
| **合规** | 抓取内容仅限**内部研究**，不得再分发 | 与他人确认后启用；文档留痕 |
| **`__biz` 撞唯一索引** | 同号多源名（如"阮一峰的网络日志" vs "阮一峰"）会冲突 | 部分唯一索引 + 登记时**按 `__biz` 复用已有源**而非新建 |
| **md 无本文 URL** | `canonical_url` 缺失 ⇒ 跨源去重只剩 `content_hash`/simhash | 有 CSV 就配对补 URL；无 CSV 时明确接受"仅内容级去重" |

### 9.2 未决问题（**需老朱拍板，方案按推荐值先写**）

| # | 问题 | 我的建议 |
|---|---|---|
| **Q1** | **订阅周期**：每日一次（20:30）还是每小时？ | **每日 20:30**（公众号更新频率低，且要多花凭证/限流额度） |
| **Q2** | **历史批量下载的触发**：接受"人工在 GUI 设范围"吗？ | 接受（MCP 无参数，这是硬约束）；前端给分步引导降低操作成本 |
| **Q3** | **CSV 是否随 md 一起投喂**（决定能否拿到权威 `published_at` 与本文 URL） | **建议要**。wechatDownload 同时导出 MD+CSV，一次 zip 上传；否则画像的时间维度会退化 |
| **Q4** | **公众号 id（`__biz`）的用途**：仅溯源展示，还是要做"跨号同文识别"？ | 先只做**溯源 + 续拉去重键**；跨号分析留待真有需求 |
| **Q5** | 是否需要**"对话/评论"数据**？ | 本轮**不做**（README 提到支持，但评论不在抽取/画像口径内） |
