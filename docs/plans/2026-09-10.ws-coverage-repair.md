# 2026-09-10 WS 命令驱动的数据覆盖度检测与补全机制

## 状态

**待实施**（方案已就绪，待确认后落地）。本方案由 2026-09-09/10 补数实战暴露的问题反向推导，见 §2。

---

## 1. 目标

让 **backend 能查看 data-cleaner（dc）的数据完整度，并通过 WS 指令 dc 执行修复与回填补全**，把今天"人肉写脚本 + 盯日志"的补数过程变成一条可复用、可观测、可远程触发的链路。

具体：

| 能力 | 说明 |
|---|---|
| 查看完整度 | backend API → WS 命令 → dc 返回覆盖度快照（最新交易日 / 标的数 / 与上一交易日比值 / 是否停滞） |
| 指令修复 | backend API → WS 命令 → dc 后台跑 `verify_and_repair`，**立即返回 accepted**，不阻塞 |
| 查看修复进度 | dc 周期性回推进度；backend 可查"修复中 / 进度 / 最近一次结果" |
| 幂等与防重 | 同一时刻只允许一个修复在跑；与 dc 自带 8:30 定时任务互斥 |

**非目标（v1 不做）**：前端 UI 按钮（仅提供 backend API）；覆盖度快照落库做历史趋势；多 dc 副本的选主/扇出。

## 2. 背景与动机（2026-09-09/10 实战复盘）

补 9-09 日线时暴露的三个真实问题，本方案逐一对应：

1. **因子库曾整体为空**：所有类别 parquet 只有一个 `2025-07-18` 的 1×5 空文件 → 调仓 `compute_target` 报"无可用因子值"。根因是因子库长期未重建，而**无人能提前发现**。
2. **日线拉取会静默残缺**：9-09 只拉到 1062/5557 只（限频中断），`check_coverage` 命中"覆盖度不足"，但**只有 dc 自己知道**，backend 无感知、无法触发修复。
3. **补数靠人肉**：本次是手写 `_backfill_0909.py` + 看守脚本轮询日志 `DONE` 才串起来。**这套"检测—修复—进度"能力应当产品化**，且由 backend 统一指挥。

- **dc 是 WS 客户端，backend 是 WS 服务端**。dc 主动拨入 `backend/app/ws/server.py:34`：


## 4. 架构

### 4.1 消息时序

```
backend API                backend(WS 服务端)         dc(WS 客户端)
    |                            |                          |
    |-- GET /coverage ---------> |                          |
    |                            |-- command.request ------>|  cmd=coverage.check
    |                            |   (corr_id=C1)           |  run_in_executor(check_coverage)
    |                            |<-- command.response -----|  corr_id=C1, data={...}
    |<-- 覆盖度快照 ------------- |   (20s 内同步返回)        |
    |                            |                          |
    |-- POST /coverage/repair -> |                          |
    |                            |-- command.request ------>|  cmd=coverage.repair
    |                            |   (corr_id=C2)           |  单飞检查 → 立即回 accepted
    |                            |<-- command.response -----|  corr_id=C2 {accepted,task_id}
    |<-- {accepted,task_id} ---- |                          |
    |                            |                          |  ...后台跑 verify_and_repair
    |                            |<-- event.pipeline.progress|  task=coverage_repair（周期回推）
    |                            |<-- command.response -----|  corr_id=C2 {done,result}（结束时）
    |-- GET /repair/status ----> |  读 conn.last_coverage    |
    |<-- {running,progress,...}- |                          |
```

### 4.2 命令表（v1）

| 命令 | 方向 | 耗时 | 语义 |
|---|---|---|---|
| `coverage.check` | backend→dc | <1s | 返回 `check_coverage()` 快照；同步等待，超时 20s |
| `coverage.repair` | backend→dc | 数十分钟 | 立即回 `{accepted,task_id}`；后台执行 `verify_and_repair()`；结束时用**同一 corr_id** 再发一次 `{done,result}` |
| `coverage.repair.status` | backend→dc | <1s | 返回 dc 侧当前修复状态（是否运行、task_id、进度） |

### 4.3 新增协议类型（两侧 `protocol.py` 同步）

```python
COMMAND_REQUEST  = "command.request"    # backend → dc
COMMAND_RESPONSE = "command.response"   # dc → backend（加入 PUSH_TYPES，享 seq/ack 与断线补发）
```

载荷助手：

```python
def command_payload(*, cmd, params=None) -> dict
def command_result_payload(*, cmd, ok, data=None, error=None, accepted=False,
                           done=False, task_id=None, progress=None) -> dict
```

### 4.4 长任务为什么必须异步

`verify_and_repair` 实测数十分钟（限频退避）。若做成同步请求/响应：WS 帧超时、HTTP 请求超时、线程占满。
故：**命令本身秒回 `accepted`，结果通过"同 corr_id 的第二次响应 + 周期性 `event.pipeline.progress`"回推**，与已有 `emit_pipeline` 进度模式（`daily_pipeline.py:87/156/193`）保持一致。

2. **覆盖度快照落库**：`conn.last_coverage` 是内存态，重启即失。若要历史趋势/告警，需建表持久化。

4. **多副本**：同一 `service_code` 多 dc 实例时，`send_command` 目前取第一个连接；真正多副本需选主或扇出（当前 dc 只 1 实例，不阻塞）。
5. **协议契约测试缺失**：`protocol.py` 注释声称有契约测试校验两侧一致，但按 `*protocol*.py` 未检索到；本方案用 hash 比对代替，建议后续补一个真正的契约测试。
6. **死配置 `WS_TOKEN`**（§3.8）：dc `config.py` 无该字段（`extra="ignore"`），建议清理或接入；两侧令牌字段名**一致**（均为 `STRATEGY_INTERNAL_TOKEN`），无需统一。
7. **`coverage.repair` 无法限定标的范围**：当前指令一定触发全市场 `verify_and_repair`（受限于 `verify_and_repair` 未透传 `symbols`）。若需"只补某几只"或做小范围冒烟，建议后续给命令加 `symbols` 参数（透传到 `backfill_universe(symbols=...)`）。

## 9. 本方案的假设（若与你的预期不符请指出，我按你的口径调整）

1. **只走 WS**，不给 dc 新增覆盖度 HTTP 端点（依据你"通过 ws 命令驱动"的表述）。
