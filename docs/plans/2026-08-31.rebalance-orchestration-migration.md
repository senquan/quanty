# 调仓编排从 data-cleaner 迁移到 backend（方案 A）部署实施方案

状态：✅ 已实施（backend 编排 + dc 行情中继 + dc 调仓下线）— 2026-08-31

## 一、目标

把"策略调仓的编排与下单"从 data-cleaner 收回 backend，使职责回到应有边界：

| 服务 | 定位 | 应负责 | 现状 |
|---|---|---|---|
| **backend** | 控制中心 + 交易中心 | 策略编排 + 持仓/现金 + 风控 + 下单 + 调仓记录 | 只有被动接单的 internal 端点 ❌ |
| **data-cleaner** | 无状态服务，可独立多实例 docker 部署 | 数据清洗/因子/回测 + **发信号**（`/strategy/scores` 只算目标持仓）+ **行情中继** | 还在编排调仓、下单、存执行记录 ❌ |

**部署形态**（已确认）：
- backend 与 data-cleaner **分属独立 Postgres 实例**（非同库）；
- data-cleaner **无状态、可水平多实例**部署；
- backend 为控制中心，**调度器只应在单一实例上启用**。

附带收益：调仓记录补上 `mode` 字段（原表 `factor.factor_strategy_executions` 无此字段，无法区分模拟/实盘）。

## 二、现状（证据）

- `data-cleaner/app/tasks/scheduler.py:158` 的 `_strategy_rebalance_job` 在交易日 9-15 点每 15 分钟触发 `scan_and_rebalance()`。
- `data-cleaner/app/strategy/rebalance.py:134` 的 `rebalance_one()` 是完整交易闭环：算目标持仓 → 调 backend `/account/internal`、`/positions/internal` → 算净买卖 → POST `/orders/internal` 下单 → 写 `factor.factor_strategy_executions`。
- backend **无任何调度能力**（全仓搜 `apscheduler|BackgroundScheduler|add_job` 为 0 命中），`backend/app` 下只有 api/core/models/schemas/services。
- 现网部署为**单副本**（根 `docker-compose.yml`：postgres / backend:8000 / redis / data-cleaner:8100，均无 scale 配置）。
- backend `main.py` 当前**无 lifespan**（只有异常处理器与路由）。

## 三、目标架构

### 3.1 迁移后的数据流

```
[backend] app/tasks/rebalance.py::scan_and_rebalance()
   │ 1. 拉启用策略        → 本地 proxy.list_strategies(active_only=True) → dc /strategies
   │ 2. 算目标持仓        → 本地 proxy.scores(config) → dc POST /strategy/scores   ← dc 只做计算
   │ 3. 读持仓 / 现金     → backend 本地 DB（直连，不再走 internal HTTP 往返）
   │ 4. 算净买卖清单      → backend（迁自 rebalance.py，含 95% 仓位、100 股取整）
   │ 5. 下单              → TradingCoordinator.place_order(source="strategy")
   │ 6. 写调仓记录        → backend 本地表 trading_rebalance_records（带 mode）
   ▼
[broker 适配层] paper(内存撮合) / live(妙想，默认 dry-run)
```

第 3 步是重要简化：原实现要两次 HTTP 往返 dc→backend 读账户持仓，迁移后直接读本地库，既少一次网络依赖，也消除了 `/positions/internal` 这类跨服务耦合。

### 3.2 部署拓扑与"多副本重复触发"问题

**前提已确认**：backend 与 data-cleaner 分属独立 PG 实例；data-cleaner 无状态可多实例扩展，backend 为控制中心。
因此调度器放 backend（控制中心，单实例），data-cleaner 保持无状态——职责与部署形态一致。
调度器内嵌 API 进程后，若 backend 扩容会重复触发，采用**双保险**：

| 层 | 措施 | 说明 |
|---|---|---|
| 部署层 | `ENABLE_TRADING_SCHEDULER` 开关（**默认 false**） | 由运维指定唯一实例开启；API-only 副本不启动调度器 |
| 数据层 | 调仓记录唯一约束 `uq(strategy_id, rebalance_date, mode)` | 即使两个实例同时触发，第二次 upsert 命中即跳过，天然幂等 |

> 未来若 backend 扩为多副本且不便指定实例，再加 **Postgres advisory lock**（`pg_try_advisory_lock`）作为增强，本期不做（现网单副本，避免过度设计）。

### 3.3 部署形态对比（本期选 A1）

| 方案 | 说明 | 评价 |
|---|---|---|
| **A1（选）** 调度器内嵌 API 进程 + 开关 | 与 data-cleaner 现有做法一致（lifespan 启停），运维最简单 | ✅ 零新增组件 |
| A2 独立调度容器 | compose 增加 `backend-scheduler` 服务，与 API 镜像相同、命令不同 | 隔离更彻底，但多一个容器要维护；扩容时更清晰 |
| A3 外部调度（cron / K8s CronJob）打 API | 无长驻进程 | 需要暴露触发端点与鉴权，调度粒度受限 |

## 四、数据模型

### 4.1 backend 新增表 `trading_rebalance_records`

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int PK | |
| strategy_id | int, index | 策略 ID（来自 data-cleaner） |
| strategy_name | varchar(128) | 冗余存名，避免列表页再查一次 |
| **mode** | varchar(16) | **paper / live（原表缺失，本次补上）** |
| rebalance_date | date | 调仓日 |
| trade_date | date null | 实际成交日 |
| target_count | int | 目标标的数 |
| orders_placed | int | 下单笔数 |
| amount | float | 下单金额 |
| status | varchar(16) | success / error / skipped |
| detail | text(jsonb) | 订单明细与错误信息 |
| created_at | timestamptz | |

- 唯一约束：`uq_rebalance(strategy_id, rebalance_date, mode)` —— **幂等兜底，防重复调仓**。
- 建表沿用项目约定：`Base.metadata.create_all(tables=[...])` + 进程内锁（见 `trading_repository.ensure_trading_tables`）。

### 4.2 历史数据迁移（跨库，已确认分库）

`factor.factor_strategy_executions`（data-cleaner 侧 `factor` schema）已有记录需迁入 backend，`mode` 统一填 `paper`（历史均为模拟盘）。

> ⚠️ **backend 与 data-cleaner 分属独立 Postgres 实例，不能做库内 `INSERT ... SELECT`。**

采用**文件中转**的两阶段脚本（对两库间网络连通性无要求）：

```
① 导出（在 data-cleaner 侧运行）
   factor.factor_strategy_executions → executions.jsonl
② 导入（在 backend 侧运行）
   executions.jsonl → trading_rebalance_records（mode='paper'）
```

- 幂等：导入按 `uq(strategy_id, rebalance_date, mode)` upsert，可重复执行。
- 若两库网络可达，可选 `--direct` 模式直连双库一次完成（非默认，避免把两套库凭证放进同一进程）。
- 迁移期间 data-cleaner 原表**不删除**，作为回滚保障。

### 4.3 下单资金分配（可配置，默认沿用）

原逻辑（data-cleaner）：`per = cash * 0.95 / n`，再按 `int(per / price / 100) * 100` 取整到手。
迁移后**改为可配置，默认与原逻辑完全一致**：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `REBALANCE_CASH_USAGE` | `0.95` | 可用资金使用率（留 5% 缓冲应对手续费/价格波动） |
| `REBALANCE_LOT_SIZE` | `100` | 下单整手股数（A 股 100 股/手） |
| `REBALANCE_WEIGHT_MODE` | `equal` | `equal`=等权（默认沿用）；`target_weight`=按目标权重分配（预留，本期不实现） |

## 七、部署步骤（零停机、可回滚）

现网为 `docker-compose up`，按以下顺序，**每步都可回退**：

| 步骤 | 动作 | 风险 | 回滚 |
|---|---|---|---|
| 1 | 部署 backend 新代码，`ENABLE_TRADING_SCHEDULER=false` | 低（只是新增代码与表） | 回退镜像 |
| 2 | 执行历史数据迁移脚本 | 低（只 INSERT，不动原表） | 删除新表数据即可 |
| 3 | 验证 `/trading/rebalances` 读本地表正确、手动 trigger 可用 | — | — |
| 4 | **关闭 dc 调仓**：部署 dc 新代码（已删 job） | 中（调仓短暂停止） | 回退 dc 镜像 |
| 5 | **开启 backend 调度**：`ENABLE_TRADING_SCHEDULER=true` 并重启 backend | 中 | 改回 false |
| 6 | 观察一个完整交易日（9:30-15:00），核对调仓记录与持仓变动 | — | 有问题执行步骤 4 的回滚 |

第 4、5 步之间会有短暂空窗（两边调度都关），建议安排在收盘后执行。

**环境变量**（根 `docker-compose.yml` 的 backend 服务）：
```yaml
backend:
  environment:
    ENABLE_TRADING_SCHEDULER: "true"   # 仅此实例开启
    BROKER_MODE: "paper"               # 默认模拟盘
    BROKER_DRY_RUN: "true"             # 实盘默认不开真单
```

**依赖**：backend `requirements.txt` 新增 `apscheduler`。

## 八、回滚方案

任一环节异常，按"最后一步优先"回退：

- **backend 调度异常**：`ENABLE_TRADING_SCHEDULER=false` 重启 → 恢复 dc 旧镜像（调仓回到 dc）。
- **下单结果不符预期**：止损开关 `BROKER_MODE=paper` 已是模拟盘，不会产生真实资金影响；核对 `trading_rebalance_records.detail` 中的逐笔订单定位问题。
- **数据错误**：新表可安全清空重跑（原 dc 表全程未删除，历史不丢）。

关键点：**data-cleaner 的 `factor.factor_strategy_executions` 与 `/strategy/scores` 全程保留**，任何时刻回退都不会丢数据或断供目标持仓。

## 九、风险与待确认

### 已确认（2026-08-31）

1. **分库**：backend 与 data-cleaner 分属独立 PG 实例 → 历史迁移走文件中转（见 4.2）。
2. **部署形态**：data-cleaner 无状态、可多实例 docker 部署；backend 为控制中心、交易中心，调度器只在单一实例启用。
3. **资金分配**：改为可配置，默认沿用 `cash*0.95/n` + 100 股取整（见 4.3）。

### 待处理风险

4. **backend 从"无状态"变为"有状态"**（内嵌调度器）。若后续引入负载均衡多副本，必须保证只有一个实例开启 `ENABLE_TRADING_SCHEDULER`，或改用 A2 独立调度容器 / advisory lock。
5. **调仓触发时点**：现 dc 为 9-15 点每 15 分钟扫描 + `trade_time` 到点判断 + 按日防重。迁移后保持同样语义；15 分钟粒度日均约 25 次无效扫描，可后续优化为每日单次。
6. **`strategy_id` 跨库引用**：backend 表只存 dc 的策略 ID（分库，无法建外键）。dc 侧删除策略后，backend 记录成悬空引用（列表页显示 ID 而非名称）。可接受，但删除策略时应提示。
7. **internal 端点去留**：本期保留（deprecated），需确认无其他调用方后再清理。
8. **信号与行情中继**（dc 新定位）本期不在改造范围内，仅作为职责边界确认。

## 十、实施结果（2026-08-31）

### 10.1 实施中发现并解决的关键问题：分库导致 backend 无法取价

原 data-cleaner 实现从 `factor.raw_bars` 取最新收盘价算股数。**分库后 backend 读不到行情**，
而 `compute_target` 返回值 `{date, weights, scores, holdings}` **不含价格**，
且 dc 原有 `GET /raw/{symbol}` 只能单标的返回全历史（30 个目标 = 30 次请求，不可接受）。

解决：按 dc 的"行情中继"定位新增批量取价接口，backend 经代理调用（一次请求覆盖全部标的）。

| 侧 | 改动 |
|---|---|
| data-cleaner | `RawBarRepository.latest_prices(symbols)` + `POST /api/v1/raw/latest-prices` |
| backend | 新增 `app/services/market_proxy.py`（`latest_prices()`） |

### 10.4 补充实施（2026-08-31，按反馈）

#### ① 风控：单笔订单上限改为按总资产比例

| 项 | 改动 |
|---|---|
| `RiskControlManager` | `max_order_value`（绝对值 10 万）→ `max_order_pct`（占总资产比例，默认 0.3） |
| 取值方式 | `max_order_value(total_assets)` 改为**方法**，返回 `总资产 × 比例` |
| 配置 | 新增 `RISK_MAX_ORDER_PCT`（默认 0.3，与 `max_position_pct` 对齐，避免另设更紧门槛） |
| 接口 | `/trading/risk-settings` 新增 `max_order_pct`；`max_order_value` 改为按当前总资产换算的有效值 |
| 前端 | `RiskSettings` 类型同步新增 `max_order_pct` |

效果（100 万账户）：单笔上限 10 万 → 30 万。此前 `top_n=5`（每笔 19 万）会被**全部拒单**，现已放行。

```

limit(1M)     = 300000.0
order_value=95000  -> True
order_value=190000 -> True    ← 原先被 10 万绝对值拒绝
order_value=300000 -> True
order_value=400000 -> False   （正确拦截，超 30 万上限）
```
