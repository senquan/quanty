### 🚀 新增功能
- **用户权限码获取接口** (`auth.py` — `/codes`)
  - 涉及模块：认证/授权、角色权限（RolePermission）、菜单权限（Menu）
  - 技术要点：使用 SQLAlchemy 2.0 的 `select().join().where()` 链式查询，通过多表关联提取用户所有权限码
  - 设计模式：依赖注入守卫 — 用 `Depends(get_current_user)` 获取当前用户，基于 `role_id` 进行权限码查找

```python
# 可复用的权限码查询模式
codes = [row[0] for row in await db.execute(
    select(Menu.permission)
    .join(RolePermission, Menu.id == RolePermission.menu_id)
    .where(RolePermission.role_id == current_user.role_id)
    .where(Menu.permission.isnot(None))
    .where(Menu.permission != "")
)]
```

### 🐛 Bug修复（模式化）
- **问题描述**：所有 FastAPI 端点返回格式不统一 — 部分返回 dict `{message: ...}`，部分返回裸 Pydantic model，部分返回列表
  - **根本原因**：多人迭代开发中，不同开发者使用了不同的返回约定
  - **解决方法**：引入统一的 `Response.success(data=...)` 包装器，所有端点改为 `response_model=Response[Type]`
  - **预防建议**：定义 API 规范文档（OpenAPI schema），CI 中校验 `response_model` 一致性

- **问题描述**：SQLAlchemy `db.delete()` 用法不一致 — 混用 `Model.delete().where()` 和 `delete(Model).where()`
  - **根本原因**：legacy codebase 从 SQLAlchemy ORM 风格迁移到 Core 风格时的过渡态
  - **解决方法**：统一使用 `from sqlalchemy import delete; await db.execute(delete(Model).where(...))`
  - **预防建议**：在代码规范中明确 SQLAlchemy 版本约定，避免 ORM/Core API 混用

### 📦 依赖变更/类型使用模式
- **Generic Pydantic Response**：`Response[Type]` — FastAPI 与 Pydantic 的泛型配合使用
  ```python
  from typing import Generic, TypeVar, Optional
  T = TypeVar('T')
  
  class Response(BaseModel, Generic[T]):
      code: int = 20000
      msg: str = "success"
      data: Optional[T] = None
      
      @classmethod
      def success(cls, *, msg: str | None = None, data: T | None = None):
          return cls(msg=msg or "success", data=data)
  ```
- **注意事项**：使用 `Response[Type]` 时，需确保 `response_model=Response[ActualType]` 精确匹配，否则 OpenAPI 文档可能错误

## 💡 经验总结

### 1. 统一的 API 响应模式是前后端契约的基础
项目采用 `Response.success(data=T)` + `Response[Type]` 泛型类型注解的模式，形成了清晰的前后端契约。**关键要点**：
- TypeVar 约束返回类型，前端 TS 可直接推断 `Promise<Response<UserInfo>>`
- `success()` 类方法作为 factory，避免每次手动构建 `{code: 200, msg..., data...}`
- OpenAPI 文档（Swagger/Redoc）能自动识别 `response_model=Response[Type]` 并生成完整的 schema

### 2. SQLAlchemy 兼容性迁移路径
从 `Model.delete().where()` (legacy ORM) → `delete(Model).where()` (SQLAlchemy Core) 是标准的迁移路径。**注意事项**：
- 旧写法在 SQLAlchemy 2.0+ 中仍可工作但有 Deprecation Warning
- 新写法需要 `from sqlalchemy import delete` 导入
- 数据库连接从 `db.session.execute()` / `db.query()` → `await db.execute(select(...))`（异步模式）

### 3. 变量命名消除歧义原则
`backtest_result`（模糊）→ `backtest_result_model`（明确）体现了**作用域歧义消除**的设计思想：**当同一上下文中出现同名/相似名的不同实体时，加 suffix/prefix 使类型意图可见**。

### 4. Comment 生命周期管理
开发过程中标记的 `H1-1: sync → async`、`H1-5: dict → model_dump()` 等 TODO 注释在完成修改后应被移除。**经验**：
- 在 commit message 中已有详细说明，代码内无需重复
- 过时的 TODO 注释会降低可读性，增加维护成本

### 5. Mock → Real Backend 迁移模式（0b4aafe）
`feat: remove mock` 一次提交了 12个前端文件变更 + 后端用户/菜单端点，涉及：
- **批量更新**：所有 `.ts` API 文件中的请求 URL、参数映射统一修正
- **联调验证**：前后端同时提交确保接口一致性
- **回测策略**：先部署后端真实接口，再替换前端 mock → real 调用
