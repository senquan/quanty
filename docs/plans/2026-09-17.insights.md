### 🐛 Bug修复
- **dc 启动即崩：迁移重放撞唯一冲突**（3cd19de，D-9 回归）
  - 现象：`UniqueViolationError: 无法创建唯一索引 idx_intel_profiles_key_ver`（键值 `(散户森, author, v1)` 重复）
  - 根本原因：`apply_migrations()` **每次启动全量重放**所有 `migrations/*.sql`（无 applied 记录表、无校验和、无版本比对）。013 建 3 列唯一索引，018 已 drop 并换成含 `as_of` 的 4 列索引；D-9 画像版本化上线后，同一 `(key,type,ver)` **合法地**存在多个 `as_of` 行（实测 14 key × 2 as_of = 28 行）→ 重启时 013 重放重建废弃索引必撞冲突
  - 解决方法：删掉 013 里那条 CREATE（018 的 `DROP INDEX IF EXISTS` 继续负责清历史遗留），并在原地注释写明原因与「不要加回来」；全新环境无影响（唯一性由 018 的 `idx_intel_profiles_key_ver_asof` 承担）
  - 预防建议（本次新增的双层防线）：
    1. **静态守卫** `test_migrations_no_dead_index.py`（4 用例）：R1 死索引检测——按文件顺序模拟 CREATE/DROP 事件，最终态不存在的索引名即违规（DROP 后再 CREATE 的合法重建不算）；R2 口径锁定——`author_profiles` 最终生效的唯一索引必须含 `as_of`；2 条自检——喂 09-16 事故形态必须被抓出、把 013 的 CREATE 加回去时 R1 能精确报出索引名（反向验证过）
    2. **重放自检** `_verify_migrations_replay.py`（长期验收工具，`.gitignore` 加 `!` 例外入库）：真正执行一次 `apply_migrations()` + 复查唯一索引口径与 as_of 版本数；退出码 0 = 可重启 dc。**改过迁移文件先跑它，别拿 dc 试**
  - 注释里的核心结论：`「迁移文件语法正确」≠「迁移能重放」`——全量重放模型下，任何 DDL 都必须对「当前数据形态」幂等

## 💡 经验总结
1. **全量重放式迁移不能留历史包袱**：「建了又被后续迁移 drop」的 DDL 每次启动都会重跑一遍，数据形态一旦演进就崩。迁移文件必须对「当前数据」幂等，废弃语句应删除并在原地留注释说明为什么删。
2. **迁移变更要配双层防线**：静态守卫（正则模拟最终态，抓死索引 + 口径漂移，快、可入库 CI）+ 重放自检（真跑一遍 `apply_migrations`，抓「语法对但重放炸」）。事故形态本身要做成自检用例（本次 R1 反向验证：加回 CREATE 能精确报出索引名）。
3. **数据口径（百分比 vs 比率）是最常见的静默错误源**：改口径时必须全链路同步——数据源优先级、裁剪阈值、回退转换、文档/数据字典。注释写明「4.85 = 4.85%」级别的显式约定，不留「应该是一致的」的模糊地带。
4. **数据源优先级按「实际数据路径」排序**：恒为空的字段排前面 = 隐式死代码；真实路径在前，潜在扩展路径降级为带注释的回退分支。
5. **「从不发生」也要显式建模**：覆盖率类指标不能靠 NaN 混过去——对从不分红标的显式写 0（首交易日 + 前向填充），幂等、不覆盖真实值，覆盖率才能趋近 100%。
6. **全栈功能上线的层序**：后端因子/存储（7512c39 先改 `fundamental.py` + `fundamental_store.py`）→ 数据回补任务 → 迁移描述 → 前端契约（`types.ts`）→ mock 引擎 → UI。前后端契约（`manualWeights`）在 types.ts 单点定义。
7. **事故写入 commit message 的模板**：现象（报错原文 + 日期）→ 根因（精确到函数:行号 + 数据形态）→ 修法（含「为什么对全新环境无影响」）→ 防线（新增测试/工具）→ 验收（崩溃时数据形态连跑两次通过）。3cd19de 是可直接复用的范例。
