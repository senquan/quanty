## 1. 目标与最终拓扑

在**一台公网服务器**上部署 backend + data-cleaner 全栈；**backend 对外**（前端浏览器访问），**dc 仅内网**（只给 backend 用）。全量迁移两侧数据后，交易/调仓/因子/覆盖度命令链路照常。

```
                公网浏览器
                    │ 443/TLS（宿主 Nginx/Caddy —— 唯一公网入口）
                    ▼
        ┌───────────────────────────┐
        │ frontend  :8080           │  nginx：静态资源 + /api 同源反代
        └─────────────┬─────────────┘
                      │ /api/ → http://backend:8000
   ┌──────────────────▼──────────────────────────────────────────────┐
   │ 公网服务器（Docker 内网 quant-network）                          │
   │                                                                 │
   │   backend :8000  ◄──ws://backend:8000/ws/dc───  data-cleaner:8100│
   │        │  └────── HTTP(cleaner_services.base_url) ──►            │
   │        │                                                        │
   │   postgres(quant_db)   postgres-factor(factor_db)   redis       │
   └─────────────────────────────────────────────────────────────────┘
```

- **8080**（frontend）：**仅绑宿主回环** `127.0.0.1:8080:8080`；由宿主 Nginx/Caddy 承接 443/TLS 转发（唯一公网入口）。
- **8000**（backend）：**仅绑宿主回环** `127.0.0.1:8000:8000`；browser 经 frontend 的 `/api` 反代访问，无需公网直连（若要独立域名直连 backend，需改回映射并补 `ALLOWED_ORIGINS`）。
- **8100**（dc）：**不对外**（compose 已去掉端口映射），仅容器网络可达。
- **5432 / 5433 / 6379**：**不映射**（compose 已去掉；如需本机调试改 `127.0.0.1:xxxx:xxxx`）。
- **单实例**：`ENABLE_TRADING_SCHEDULER` / `ENABLE_FACTOR_SYNC` / `ENABLE_PORTFOLIO_VALUATION` 等只在唯一实例开启（compose 已置 `ENABLE_TRADING_SCHEDULER=true`、`ENABLE_FACTOR_SYNC=true`）；dc 同理只能一个实例。
- **免 CORS**：前端构建用 `VITE_GLOB_API_URL=/api/v1`（同源），由 frontend 的 nginx 反代到 backend；因此 backend 的 `ALLOWED_ORIGINS` 仅在"前端独立域名直连 backend"时才需要。

## 2. 迁移内容清单（实测）

源机实测：`DB=quant`、`TIMEZONE=Asia/Shanghai`。**本地 backend 与 dc 共用同一个库 `quant`，但分属两个 schema**——所以导出必须**按 schema 拆分**：
- backend → `-n public`
- dc → `-n factor`

| 迁移项 | 实测体积 | 明细 |
|---|---|---|
| **backend `public` schema** | **1.3 MiB** | 18 表 / 15 序列 |
| **dc `factor` schema** | **4,050.9 MiB** | 12 表 / 2 函数 / 4 序列 |
| **因子 parquet 库** | **2,462.5 MiB** | `data/factors/<cat>/<date>.parquet`，11,556 文件（9 类 × 1,284 日）|
| **合计** | **≈ 6.4 GiB** | |

### 2.1 backend `public`（18 表，全部很小）

| 表 | 行数 | 表 | 行数 |
|---|---|---|---|
| factor_registry | 51 | strategies | 2 |
| trading_orders | 28 | backtest_results | 1 |
| trading_positions | 21 | instruments | 10 |
| trading_trades | 21 | menus | 2 |
| portfolio_daily_values | 7 | **users** | **1** |
| trading_rebalance_records | 5 | roles | 0 |
| portfolios | 2 | role_permissions | 0 |
| cleaner_services | 1 | signals / execution_reports / watchlist | 0 |

> 三个"身份相关"的表（`users` / `roles` / `menus` / `role_permissions`）**必须迁移**，否则登录/菜单直接不可用。

### 2.2 dc `factor`（12 表）

`raw_bars` 2,294.7 MiB / 6,140,633 行；`daily_basic` 1,682.8 MiB / 11,189,235 行（2018 起）；`finance_reports` 65.9 MiB / 220,017；`trading_status` 4.95 MiB；`industries` 1.79 MiB；`stock_info` 0.41 MiB；其余 6 张 `factor_*`/`definitions`/`metrics`/`pipeline_runs` 合计 < 0.5 MiB。

### 2.3 不迁移

- dc `data/raw/*.parquet`（PG 为主存储，实测为空）；
- Redis（键 `factor:heartbeat` / `raw_backfill_progress`，可重建）；
- `data/quarantine`（失败快照，可选）；
- **前端**：无数据可迁 —— `apps/web-ele/dist` 是**构建产物**，目标机重建即可（见 §6.1）。故迁移总量仍为 **≈6.4 GiB**。

### 2.4 增长预期

每交易日 ≈ **5.5 MiB**（raw_bars ~2.1 + daily_basic ~0.83 + 因子parquet ~2.14 + trading_status ~0.4），**约 1.3 GiB/年**；backend 侧数据量可忽略。
→ **建议目标盘 ≥ 50 GiB SSD（推荐 100 GiB）**，预留 dump/备份/镜像/日志；若日后回补至 2010（全量）总量约 12 GiB。

## 4. WS 令牌链路（上线前必读，含一处真实地雷）

| 环节 | 代码位置 | 实际使用的字段 |
|---|---|---|
| dc 拨入 backend 时携带的令牌 | `data-cleaner/app/ws/client.py:117` | dc 的 `STRATEGY_INTERNAL_TOKEN` |
| **backend 握手校验** | `backend/app/ws/server.py:55` | **`STRATEGY_INTERNAL_TOKEN`** |
| backend 启动判空告警 | `backend/main.py:38-39` | `STRAT_INTEGRATION_TOKEN`（**另一个字段**）|
| dc 调 backend 内部下单端点 | dc `STRATEGY_INTERNAL_TOKEN` → backend `/trading/orders/internal` | `STRATEGY_INTERNAL_TOKEN` |

**地雷**：`main.py:38-39` 判空的是 `STRAT_INTEGRATION_TOKEN`，而真正校验的是 `STRATEGY_INTERNAL_TOKEN`。若照仓库文档（`CLAUDE.md:73`、`data-cleaner/README.md:94`、两个 `.env.example`）**只配 `STRAT_INTEGRATION_TOKEN`**，则 `server.py` 的 `expected=""` → **握手完全不校验令牌**（且不会告警）—— 属静默的安全降级。

**处置**：权威字段是 **`STRATEGY_INTERNAL_TOKEN`**，两侧填**同一个强随机值**；同时把 `STRAT_INTEGRATION_TOKEN` 也设成同值以消除误导性告警；并建议后续修 `main.py` 的判空字段与相关文档（见 §9）。

### 5.2 `SECRET_KEY` **必须沿用原值**（否则 dc 调用会静默全挂）

- 迁移过来的 `api_key` 密文**无法解密** → backend 调 dc 时鉴权失败（dc 配了 `API_KEYS` 时全 401/403，且是运行时才暴露）；
- 且所有既有用户 JWT 失效（重新登录即可，影响可接受）。

**处置**：把**源机 `.env` 的 `SECRET_KEY` 原样带到目标机**（或用 `credential` 重新加密一遍 api_key）。

**verify**：目标机启动后 `POST /api/v1/cleaner/{code}/sync` 能拉到 dc 因子（证明 api_key 可解密并通过 dc 鉴权）。

### 步骤 0.0（推荐）：用脚本一键完成「导出 / 校验 / 恢复」

`scripts/deploy/migrate_data.py`（跨平台，**源机可为 Windows**）把步骤 2、3、5、6 自动化，并额外产出**行数清单**用于导入后断言：

```bash
# 源机：导出（生成 *.dump / factors.tgz / SHA256SUMS / manifest.json）
python scripts/deploy/migrate_data.py export \
    --pg-url "postgresql://<user>:<pwd>@127.0.0.1:5432/quant" \
    --factor-dir data/factors --out ./migrate

# 目标机：恢复两个库 + parquet，并逐表断言行数（默认走 docker compose）
```

要点：

- 任何子命令都可加 `--dry-run` 只打印将执行的命令；`import` 另支持 `--mode local`（目标机非 docker 时）；
- 源库时区若非 `Asia/Shanghai` 会告警（对应风险 4）。

### 6.2 宿主反向代理（推荐）

宿主 Nginx/Caddy 承接 TLS，只需把 443 转给 **frontend:8080**（`/api` 由 frontend 内部再转给 backend）：
```nginx
location / { proxy_pass http://127.0.0.1:8080; proxy_set_header Host $host; }
```
> 若走拓扑 B（dc 跨机），WS 用 `wss://`：反代需转发 `Upgrade`/`Connection` 头，且**空闲超时 > 15s**（= WS ping 间隔）。
