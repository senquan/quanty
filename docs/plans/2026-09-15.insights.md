- **微信公众号文章自动投喂方案**（P0/P1/P2 分期）
  - 涉及模块：dc `app/intel/`、backend `/api/v1/intel/upload`、前端 `news-analysis/components/article-upload.vue`
  - 技术要点：
    - **三机同机假设取证后才敢直连**：dc/backend/wechatDownload 都在同一 Windows 机器（证据锚定到 `backend/app/core/config.py:55 INTEL_CLEANER_BASE_URL=127.0.0.1:8100`），所以 dc 可直连 MCP `127.0.0.1:4545`，不需要额外网关。
    - **能力边界先盘点再设计**：wechatDownload 本地 MCP 4 个 tool 中，`batch_download_articles` 参数为 `{}`（下载范围只能在 GUI 配）⇒ "每日读最新"不能靠它，改用 `export_article_data` 元数据差集 + 逐篇 `single_article_download`；远程 fallback 只有 `wechat`/`wechat_collection`，无批量/导出能力。
    - **公众号 id = 文章 URL 的 `__biz`（base64）**，零依赖即可提取；`get_public_account_id` 拿的是凭证，必须微信客户端点链接，半自动。
    - **P0 = 解析层，零 MCP 依赖，可独立验收**：真正的拦路虎是现有 `_parse_plain`（`ingest/manual.py:273`）只拿文件名当标题、`author` 恒为空，而画像按 `documents.author` 分组 ⇒ 照现状接入，271 篇文章全归"无作者"，画像功能等于没做。
    - **解析逐条降级**：实测 example/ 下 9 篇 md 已有 4 种格式（# 标题时有时无、作者行 3 种写法、日期行仅新版有、混入非微信 md）⇒ 解析器必须逐条降级而非整篇判废。
  - 设计模式：复用现有 inbox 通道（`run_wechat_watch()` 子目录名=公众号名，处理后移 `processed/` 幂等）+ 三级幂等去重（external_id → canonical_url → content_hash）+ simhash 转载识别。

## 💡 经验总结

1. **设计文档里的「取证式结论」写法值得学**：`f1a8491` 每个关键结论都带代码位置证据（`config.py:55`、`manual.py:273`）和实测数据（9 篇 md 4 种格式），而不是假设。方案评审时可直接核对证据链。
2. **能力边界盘点先于方案设计**：第三方工具（MCP）先逐 tool 列参数/可用范围表，发现 `batch_download_articles` 无参数后立刻调整方案（差集 + 单篇），避免了设计在不存在的能力上。
3. **"下载不是问题，解析才是"的模式**：接入外部内容源时，真正的风险通常在下游消费端（画像按 author 分组），P0 应切在消费端契约（md 必须带 author/标题/发布时间）上，并且做成零外部依赖可独立验收。
4. **文档日期前缀约定**（本项目现行标准）：`YYYY-MM-DD.<主题>.md`，plans=设计方案、memo=完成总结；目录基础设施（README/log/template）豁免前缀。后续日报文件命名（`2026-09-15.report.md` 形式）与 09-11 前缀约定不冲突——日期前缀即 `2026-09-15.`。
5. **注释级文档同步的验证策略**：改 SQL 迁移注释前先确认执行器无校验和；改 .py 引用前先确认 import 路径。全部用定向测试收尾（3 passed / 39 passed），而非全量回归。
