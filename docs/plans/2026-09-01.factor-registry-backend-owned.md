# 因子底册库归属 backend（关联 dc 源，dc 连接状态即因子可用状态）

状态：📋 待实施 — 2026-09-01

## 1. 目标

1. **因子底册库数据存于 backend 端**：`/api/v1/factors` 读本地库，不再每次实时代理 data-cleaner。
2. **关联 dc 源**：每条因子记录归属到具体的清洗服务实例。
3. **dc 连接状态 = 因子可用状态**：不再单独维护"因子可用性"，由 dc 实例的连通性直接表达。

附带收益：dc 宕机时因子页**仍能打开**（只是标记为不可用），而不是像今天这样整体超时
（参见本次排查：dc 僵死导致 `/api/v1/factors?with_metrics=true` 10s 超时）。

### 1.1 入库语义（2026-09-01 明确）

- **入库 = 在 backend 注册**：`POST /api/v1/cleaner/{code}/factors/import` 就是在
  `factor_registry` 中登记一条记录（`is_enabled=True`）。除此之外没有别的"入库"动作。
- **底册只显示已入库的**：`GET /api/v1/factors` 只返回 `factor_registry` 中
  `is_enabled=True` 的因子；**未入库的因子不出现在底册**。
- 未入库但 dc 侧存在的因子，只在**远端因子列表** `GET /api/v1/cleaner/{code}/factors`
  中可见（带 `imported` / `is_enabled` 标记），供用户在"导入"界面勾选注册。
- 因此 `sync_factors` **只刷新已入库因子的口径与 metrics，不新增未入库因子**，
  保持"registry 里每一行都是已注册因子"的干净语义。

## 2. 现状：已有资产（不是从零建）

| 资产 | 位置 | 说明 |
|---|---|---|
| `factor_registry` 表 | `app/models/cleaner.py:57` | 已有 `service_code` **外键**关联 `cleaner_services`，含 name/category/frequency/description/formula/data_source/is_enabled/last_sync/raw |
| `CleanerService` 表 | `app/models/cleaner.py:23` | 已有 `status`(online/offline/degraded/unknown)、`last_heartbeat`、`qos` |
| `sync_factors()` | `app/services/cleaner_gateway.py:216` | 已能把 dc 因子口径 **幂等 upsert** 进 `factor_registry` |
| 手动同步端点 | `app/api/api_v1/endpoints/cleaner.py:157` | `POST /cleaner/{code}/sync`，内含 `poll_qos` 先刷新状态 |
| 本地底册读端点 | `cleaner.py:239` | `GET /cleaner/factors/registry`（读本地表） |

**真正的缺口：**
- `/api/v1/factors`（前端因子页在用的底册库接口，见 `factor_library.py`）**仍每次实时代理 dc**。
- `factor_registry` **没有 metrics 字段**，前端 `with_metrics=true` 拿不到效能指标。
- 可用性由 `factor_strategy_proxy.factor_availability()` 单独回源 dc `/strategy/factors/availability` 维护，与本需求语义不一致。

## 3. 目标架构

```
                    ┌─────────────────────────────┐
  定时 / 手动触发    │  backend                     │
  ────────────────► │  factor_sync                 │──── GET /api/v1/factor?include_metrics=true ──► data-cleaner
                    │  (cleaner_gateway 增强)       │◄──── definitions + latest metrics ────────────
                    │        │                      │
                    │        ▼                      │
                    │  factor_registry (本地持有)    │
                    │   ├ service_code → dc 源      │
                    │   └ metrics (最新一期)         │
                    └──────────┬───────────────────┘
                               │
        GET /api/v1/factors ───┘  ← 只读本地，dc 挂了也能返回
                    └ 每条因子附 available = 该 service 的连通状态
```

- **读路径**：`/api/v1/factors`、`/{code}` → 只读本地 `factor_registry`。
- **写路径**：创建/更新/删除自定义因子 → **先写 dc**（dc 计算因子值需要定义），成功后同步回本地。
- **必须实时回源的接口**（本地无数据，需明确超时与错误语义）：`/correlation`、`/ai-generate`。

## 4. 数据模型变更

`factor_registry` 增加效能指标字段（存**最新一期**，与前端 `with_metrics` 需求对齐）：

| 新增列 | 类型 | 说明 |
|---|---|---|
| `metrics` | JSON null | 最新一期指标快照：`{as_of_date, ic_mean, ic_std, ir, sharpe_ratio, max_drawdown, win_rate}` |
| `metrics_synced_at` | datetime null | 指标同步时间 |

> 选择"单表 + JSON 列"而非独立 `factor_registry_metrics` 表：前端只消费最新一期，
> 独立表会带来 join 与历史数据维护成本，属于过度设计。

---

## 5. 同步策略

| 触发方式 | 说明 |
|---|---|
| **定时同步**（新增） | backend 已有 APScheduler（`app/tasks/scheduler.py`）。新增任务：按 `FACTOR_SYNC_INTERVAL_MIN`（默认 60 分钟）对所有 `is_active` 的 dc 实例执行 `sync_factors` |
| **手动同步**（已有） | `POST /api/v1/cleaner/{code}/sync` 保留，并在同步时一并拉 metrics |

同步内容：调 dc `GET /api/v1/factor?include_metrics=true`（**单次批量**，dc 侧已是批量查询，不是 N+1）。
**只更新 `factor_registry` 中已存在的（已入库）记录**，刷新口径、`metrics`、`metrics_synced_at`；
dc 新增但**未入库**的因子**不落库**（见 §1.1）。
同步前先 `poll_qos(svc)` 刷新 dc 状态；dc 不可达时**保留本地旧数据**，仅更新状态。

## 6. 可用性语义（dc 连接状态即因子可用状态）

- 因子 `available` = 其 `service_code` 对应 `CleanerService.status`：
  - `online` / `degraded` → `available = true`
  - `offline` / `unknown` → `available = false`
- `GET /api/v1/factors` 响应中每条因子附 `service_code` 与 `available`；
  顶层附 `services: [{service_code, status, last_heartbeat}]` 便于前端提示。
- **废弃** `factor_strategy_proxy.factor_availability()` 的独立回源逻辑，
  改由本地 `factor_registry` + service 状态推导，不再打 dc。
- 前端 `factorAvailabilityApi()` 的返回契约 `{code: bool}` **保持不变**（前端无需改动），
  只是数据来源由 dc 实时查询改为本地推导。

## 7. 接口变更

| 方法 | 路径 | 变更 |
|---|---|---|
| GET | `/api/v1/factors` | **改读本地** `factor_registry`，**只返回已入库的**（`is_enabled=True`）；支持 category/search/with_metrics；附 `service_code`、`available`，顶层附 `services` 状态 |
| GET | `/api/v1/factors/{code}` | 改读本地；metrics 从 `metrics` JSON 列取 |
| POST | `/api/v1/factors` | 先写 dc，成功后同步回本地（双写） |
| PUT / DELETE | `/api/v1/factors/{code}` | 同上（先 dc，再同步本地） |
| POST | `/api/v1/factors/correlation` | 保持回源 dc，但明确超时（见 §9） |
| POST | `/api/v1/factors/ai-generate` | 保持回源 dc |
| GET | `/api/v1/factor-strategies/factors/availability` | 改为本地推导，契约不变 |
| POST | `/api/v1/cleaner/{code}/sync` | 增强：一并同步 metrics |

## 8. 实施步骤

```
1. factor_registry 增加 metrics / metrics_synced_at 列
   → verify: 启动后表结构更新；旧数据不受影响

2. cleaner_gateway.sync_factors 增强：单次批量拉 definitions+metrics，
   **只更新已入库记录，不新增未入库因子**
   → verify: 已入库因子 metrics 被刷新；dc 侧未入库因子不会出现在 factor_registry

3. /api/v1/factors 改读本地：只返回已入库的，附 available 与 services 状态
   → verify: 未入库因子不出现在响应中；断开 dc 后仍 200 且 available=false，不再超时
   （注：底册为空不是 bug——用户尚未在"导入"界面勾选入库；不做"读时兜底同步"，
   因为 sync_factors 只更新已入库记录，无法自动填充）

4. 写路径双写：创建/更新/删除自定义因子后同步回本地
   → verify: 创建因子后本地表立即可见

5. availability 改本地推导，契约保持 {code: bool}
   → verify: 与旧接口返回值结构一致，前端无需改动

6. 加定时同步任务 + FACTOR_SYNC_INTERVAL_MIN
   → verify: 开关关闭时不注册 job；开启后按周期同步且 dc 不可达时保留旧数据
```

## 9. 待确认

1. **metrics 是否只需最新一期**？若后续要看指标时间序列，则应建独立表而非 JSON 列。
   （本方案按"只需最新一期"实施，与前端当前消费方式一致。）
2. **定时同步开关**：backend 调度器目前只有 `ENABLE_TRADING_SCHEDULER` 一个总开关，
   多副本部署时同样只能单实例启用。因子同步是否复用同一开关，还是单独加
   `ENABLE_FACTOR_SYNC`？（倾向复用同一开关，减少配置项。）
3. **自定义因子是否必须与 dc 双写**？若确定"底册完全由 backend 持有、dc 只做计算"，
   则 dc 需要在计算时回查 backend 拿定义 —— 这会让 dc 反向依赖 backend。
   （本方案按"先写 dc 再同步本地"实施，避免 dc 反向依赖。）
4. **超时阈值**：`factor_proxy.DEFAULT_TIMEOUT = 10.0` 偏紧（曾导致超时），
   建议提到 30s 与 `factor_strategy_proxy` 对齐 —— 是否一并调整？
