# data-cleaner 根目录脚本归置策略（D-13）

> 来源：`docs/memo/intel-audit-2026-09-10.md` D-13 ——「一次性脚本散落 dc 根目录」。
> 结论：**不搬家**（移动会破坏 docs 里的引用与肌肉记忆），改为**用命名前缀表达生命周期**，
> 并把口径写进 `.gitignore` 注释与本文件。

## 现状（2026-09-11 盘点）

`data-cleaner/*.py`（**根目录**）共 **78 个**：**52 个**已跟踪 + **26 个**未跟踪（被忽略）。
所谓"散落"其实是**三层**混在一个平铺目录里：

| 层 | 前缀 | 数量级 | 是否入库 | 说明 |
|---|---|---|---|---|
| ① 长期 CLI 入口 | `_p1_*` ~ `_p4_*` | ~15 | ✅ 入库 | 分阶段的操作入口（gate_eval / build_profiles / build_factors / acceptance …） |
| ② 长期验收工具 | `_verify_d4_task.py`、`_d8_verify.py`、`_d8_spotcheck.py` | 3 | ✅ 入库（`.gitignore` 显式 `!` 例外） | 可重复跑、有新需求时还要用 |
| ③ 一次性探针 | `_dbg_*` `_diag_*` `_test_*` `_q_*` `_poll_*` `_repair_*` `_rebuild_*` `_manual_*` `_verify_*`（除例外） | 26 | ❌ 忽略 | 排查完即弃，留着只会干扰 grep |

## 规则

1. **长期入口用 `_p<阶段>_<动作>.py`**（如 `_p3_eval.py`）。该前缀**不在任何忽略规则里** ⇒ 天然入库。
2. **一次性探针**必须用上表的③类前缀命名 ⇒ 自动被 `.gitignore` 忽略。
   最常用的是 `_dbg_`（调试）、`_q_`（随手查库）、`_poll_`（轮询等待）、`_verify_`（临时校验）。
3. **探针升级为长期工具时**，在 `.gitignore` 的「例外」段加一行 `!data-cleaner/<name>.py`，
   并在此文件登记（说明它验的是什么）。
4. **不要**把探针提交进库再删 —— 历史里的噪音清不掉；宁可一开始就忽略。

## 为什么不真搬进子目录

- `docs/` 与 `scripts/` 里有大量以 `_p3_eval.py` 这类**裸文件名**写的引用，搬家即断链；
- 这些脚本以 `sys.path.insert(0, ".")` + `from app.intel import ...` 运行，**依赖 cwd = dc 根**，
  移进子目录会改变 `sys.path` 语义、需要逐个改；
- 收益（少几个文件）远小于风险（断链 + 回归）。

> 结论：D-13 的实质问题是**"没有归置策略"**，不是"文件放错了目录"。本文件 + `.gitignore`
> 注释即策略。**已闭环。**
