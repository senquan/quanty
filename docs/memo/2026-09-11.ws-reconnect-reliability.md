# 2026-09-11 WS 长连接静默失效：排查、自愈与告警

> 类型：事故复盘（incident review）
> 相关：WS 通道设计 `docs/plans/2026-09-04.ws-dc-backend.md`；部署与迁移 `docs/plans/2026-09-10.dc-public-deploy-and-data-migration.md`

## 1. 摘要

- **现象**：dc（data-cleaner）进程健康（`GET /api/v1/qos` → 200），但到 backend 的 WS 长连接**永久断开且不再重连**，表现为 backend `GET /ws/status` 的 `connections: 0`。
- **影响**：经 WS 的**数据覆盖度检测 / 修复命令通道全部不可用**（`GET /api/v1/cleaner/{code}/coverage` 直接 503）；因子变更广播、QoS 推送同样静默失效。
- **发生**：2026-09-10、2026-09-11 各一次，**均为人工查询时才发现**。
- **结论**：dc 的重连循环 `WSClient._run` 存在「无结束回调 / 无看门狗 / 无卡死检测」三处缺口；且**两侧都缺乏主动发现手段**。已补齐自愈 + 告警 + 可观测性。
- **未决**：首次触发的根因**未取到证据**（旧日志被重启覆盖），见 §6。

## 3. 根因分析

重连逻辑位于 `data-cleaner/app/ws/client.py`。四个失效模式：

| # | 失效模式 | 说明 |
|---|---|---|
| **FM1** | 任务静默死亡 | `_run` 由 `asyncio.create_task` 启动（`start()` :162），**既无 `add_done_callback` 也无任何 `await`**。一旦因异常退出或被取消，无人知晓、无人拉起 |
| **FM2** | 退避语句无保护 | 循环尾部 `await asyncio.sleep(next(delays))` 不受保护——任何异常都会让整个 `while` 重连循环终止 |
| **FM3** | 无重建入口 | 只有 `stop()`（:228）会重建任务，而正常运行期间永不调用 |
| **FM4** | 卡死不可辨 | 若 `_run`（:345）卡在 `connect()` / `_session`，任务仍"活着"、`/qos` 仍 200，但再也不会重连 —— **与观测完全吻合** |

**放大因素：完全不可观测。** dc 自身 `/qos` 不暴露 WS 状态，只能去 backend 的 `/ws/status` 看；而 backend 侧也没有任何主动检查 —— 于是"静默失效"可持续数小时无人察觉。

## 4. 修复

### 4.1 dc 侧：自愈 + 可观测

| 改动 | 位置 |
|---|---|
| `_run` 任务加结束回调，记录「被取消 / 异常退出 / 意外结束」 | `client.py:181` `_on_run_done` |
| 新增看门狗 `_supervise`：任务已结束 → 重拉；任务活着但**超 300s 未连上** → 取消并重建 | `client.py:192` |
| `stop()` 一并取消看门狗 | `client.py:228` |
| 退避 sleep 包 `try/except`（`CancelledError` 重抛，其它记录后继续） | `client.py` `_run` 尾部 |
| `_run` 入口记录 `_run_started_at`；看门狗基准取 `max(上次连上, 本轮启动)` —— 否则"一次都没连上"的场景永不触发 | `client.py:345` |
| `/qos` 增加 `system.ws` 字段（`enabled / connected / uri / instance_id / last_acked_seq / …`） | `data-cleaner/app/core/qos.py` |

### 4.2 backend 侧：主动发现

| 改动 | 位置 |
|---|---|
| 记录每个 `service_code` 的上次在线时刻；新增 `known_service_codes()` / `last_connected_at()` / `mark_seen()` / `disconnect_report()` | `backend/app/ws/registry.py:162 / 168 / 172 / 182` |
| 新增 60s 定时告警任务（仅 `WS_ENABLED` 时注册），**同服务 600s 内不重复告警**防刷屏 | `backend/app/tasks/scheduler.py:126`（注册于 :236） |
| `GET /ws/status` 输出 `disconnect_alert_sec` / `disconnect_alerts`（**免鉴权**，便于运维直查） | `backend/app/ws/server.py` |
| 新增配置 `ENABLE_WS_DISCONNECT_ALERT`、`WS_DISCONNECT_ALERT_SEC`(300)、`WS_DISCONNECT_ALERT_CHECK_SEC`(60)、`WS_DISCONNECT_ALERT_EVERY_SEC`(600) | `backend/app/core/config.py` |

告警样例：
```
WS 断连告警：清洗服务 cleaner_dev 已失联 378s（阈值 300s，曾连接过）
—— 覆盖度检测 / 修复命令通道不可用，请检查 dc 进程与 WS 配置
```

### 4.3 判据的一个关键设计

失联基准取 **`max(上次连上时刻, 进程启动时刻)`**。若只看"上次连上"，backend 重启后 dc 再也没连上时该值为空 → 判据永不成立 → **恰好漏掉最该告警的场景**。

## 5. 验证

### 5.1 看门狗定点测试（打桩 `_run`）
- **任务静默结束**：2.6s 内重拉 3 次 ✅
- **任务卡死**：6s 内判定卡死并重建 3 次 ✅

### 5.2 告警判定逻辑（5 场景）
连接中 → `[]`；刚断开 → `[]`；超时·曾连过 → `ever_connected=true`；超时·从未连上 → `ever_connected=false`；阈值调大 → `[]` ✅

### 5.3 告警演练（真实阈值 300s，未改配置）

| 时刻 | 事件 | `disconnect_alerts` |
|---|---|---|
| 06:17:35 | 停 dc | — |
| 06:20:18 | 断连 163s | ⚠️ **已告警，`down_seconds=1326.5`** ← 发现缺陷 |
| 06:21:49 | 修好后重启 dc，连上 | `[]` |
| 06:22:14 | 再次停 dc | — |
| 06:24:42 | 断连 148s | `[]` ✅ 不再提前误报 |
| 06:28:15 | 断连 361s | `[{cleaner_dev, 378.2, ever_connected:true}]` ✅ 按时触发 |
| 06:28:55 | 重启 dc | `[]` ✅ 自动消除，`connections:1` |

### 5.4 演练中发现并修复的缺陷

`down_seconds` 曾把**连接存续时长算进失联**：实际仅断连 163s 却报 1326.5s → 一断线就误告警，300s 阈值形同虚设。

- 根因：只在 `register()` 记录时刻，**连接存续期间不刷新**；dc 连了 19 分钟后断开，这 19 分钟被全部计入。
- 修复：新增 `registry.mark_seen()`，在 `server.py` 接收循环**每收到一条消息**即刷新（心跳 30s → 误差 ≤ 一个心跳周期）。修复后实测 `378.2s` vs 实际 `361s`，准确。

## 6. 遗留与建议

1. **首次触发的根因未取证**：旧 dc 日志在重启时被覆盖，无法确认是"任务死"还是"卡死"。本轮做的是**不可复现条件下的稳健化**——两类都能自愈，且下次会留下明确日志（`_on_run_done` + `/qos` 的 `ws` 字段）。
2. **建议将 dc 标准输出长期落盘**（systemd journal 或 `>> logs/dc.log`）。有了它，下次可直接定位，不必再靠推断。
3. 告警目前只写日志 + `/ws/status`；如需 webhook / 邮件，需接外部通知通道。
4. 生产部署时确认告警参数（见部署指南附录 A 的 backend `.env` 模板）。
5. ✅ **已落实（日志落盘）**：
   - 本机：`data-cleaner/_run_real_dc.ps1` 改为**带时间戳 + 轮转**落盘
     （`data-cleaner/logs/dc-<时间戳>.{out,err}.log`，默认保留 10 份，`-Keep N` 可调）。
     此前是 `>` 覆盖写 —— 正是 §6.1 证据丢失的直接原因。
   - 生产：`docker-compose.yml` 增加 `x-logging`（json-file，10 × 50MiB 轮转）；
     并提供 `scripts/deploy/quant-stack.service` 用于开机自启与优雅停机。
   - 详见部署指南 §6.3。
